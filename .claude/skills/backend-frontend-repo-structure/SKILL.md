> This skill is intended to auto-trigger by context (e.g., when working on a repository
> containing both backend and frontend); it is not meant to be invoked ad hoc by name.

# 1. Purpose

This skill defines the architectural rules governing the boundary between
backend and frontend in a full-stack repository.

Its primary goal is to maintain the following invariant:

```text
Pydantic models
    ↓
FastAPI endpoints + response models
    ↓
OpenAPI
    ↓
Orval
    ↓
Generated TypeScript models/client
    ↓
Optional frontend API/application layer
    ↓
React components
```

The backend OpenAPI schema is the canonical machine-readable API contract.

The frontend MUST consume artifacts generated from this contract rather than
maintaining an independent representation of the backend API.

This skill defines architectural invariants.

It MUST NOT force a repository layout when the starter repository already
provides a reasonable structure.


# 2. Inspect the repository before changing it

Before creating directories, moving files, or introducing API infrastructure,
inspect the existing repository.

Identify at least:

- backend and frontend locations;
- Python project structure;
- frontend package manager;
- existing API/client modules;
- existing Orval configuration;
- existing Axios or Fetch configuration;
- Vite configuration and development proxy;
- environment-variable conventions;
- OpenAPI endpoint;
- FastAPI route prefixes;
- OpenAPI tags and operation IDs when relevant;
- existing scripts for client generation;
- existing generated files.

Preserve the starter repository organization whenever reasonable.

Do NOT restructure a repository only to make it match an example from this
skill.

Prefer:

```text
adapt tooling to the repository
```

over:

```text
adapt the repository to the tooling
```


# 3. Repository structure

The following structure is illustrative, not mandatory:

```text
<repo>/
├── backend/
│   ├── pyproject.toml
│   ├── src/
│   └── tests/
│
├── frontend/
│   ├── package.json
│   ├── orval.config.ts
│   └── src/
│       └── api/
│           ├── generated/        <- owned by Orval
│           ├── http-client.ts    <- optional custom HTTP client / mutator
│           └── services/         <- optional application API abstraction
│
├── scripts/
│   └── generate_api_client.sh    <- optional
│
└── README.md
```

Directory names such as `backend`, `frontend`, `src/api`, `services`, or
`generated` are NOT mandatory.

If the starter uses names such as:

```text
server/
web/
client/
app/
lib/api/
```

preserve them unless there is a concrete reason to change them.

The important invariant is responsibility separation, not exact paths.


# 4. Generated-code boundary

Generated frontend API artifacts MUST be isolated in a clearly identifiable
generated-code location.

For example:

```text
frontend/src/api/generated/
```

Everything inside this area is owned by Orval.

Rules:

- Never manually edit Orval-generated files.
- Never patch generated functions to fix integration problems.
- Never manually rename generated operations.
- Never manually duplicate generated request or response models.
- Regenerate artifacts when the OpenAPI contract changes.
- Configure Orval paths to match the repository structure.
- Let Orval control the internal layout of its generated directory.

The internal structure of `generated/` may change according to the Orval
configuration.

For example, a configuration using:

```ts
mode: 'single'
```

may produce a small number of files, while:

```ts
mode: 'tags-split'
```

may produce directories grouped by OpenAPI tags.

Do not make application code depend on an assumed generated directory layout
without inspecting the actual generated exports.


# 5. Backend API contract

The backend is the source of truth for the API contract.

With FastAPI, the generated OpenAPI schema is normally exposed at:

```text
GET <backend-base-url>/openapi.json
```

`/openapi.json` is a runtime representation generated by FastAPI.

Do not manually maintain a second OpenAPI contract representing the same API
unless the repository already intentionally uses an OpenAPI snapshot workflow.

Backend request and response contracts should be represented using Pydantic
models whenever appropriate.

Example:

```python
class TicketResponse(BaseModel):
    model_config = ConfigDict(extra="forbid")

    id: str
    status: Literal["pending", "processing", "done"]


@app.get(
    "/api/tickets/{ticket_id}",
    response_model=TicketResponse,
)
async def get_ticket(ticket_id: str) -> TicketResponse:
    ...
```

The frontend TypeScript representation of `TicketResponse` MUST come from the
generated OpenAPI contract rather than from a manually maintained equivalent.


# 6. OpenAPI operation IDs

Generated TypeScript function names depend on OpenAPI operation IDs.

Before working around an inconvenient generated function name in the frontend,
inspect the corresponding OpenAPI `operationId`.

If stable and readable generated operation names materially improve the
implementation, prefer fixing the API contract rather than patching generated
TypeScript.

FastAPI can explicitly define a unique operation ID:

```python
@app.post(
    "/api/tickets/{ticket_id}/acquire",
    operation_id="acquireTicket",
)
async def acquire_ticket(ticket_id: str):
    ...
```

Operation IDs MUST be unique across the API.

Do not introduce custom operation IDs everywhere unless they provide actual
value.

In particular, do not spend implementation time renaming every operation merely for
cosmetic reasons.

Use explicit operation IDs when generated names cause real readability,
maintainability, or integration problems.


# 7. Orval configuration

## 7.1 Configuration file

When creating a new Orval configuration, prefer:

```text
frontend/orval.config.ts
```

using `defineConfig`.

If the starter already contains a working Orval configuration, preserve its
location and supported format unless a change is necessary.

Example baseline:

```ts
import { defineConfig } from 'orval';

export default defineConfig({
  backend: {
    input: {
      target: 'http://localhost:8000/openapi.json',
    },

    output: {
      mode: 'single',
      client: 'axios-functions',

      target: './src/api/generated/client.ts',
      schemas: './src/api/generated/models',
    },
  },
});
```

The paths and backend URL above are examples.

Adapt them to the repository and its existing environment configuration.


# 8. Orval `mode` and `client` are independent concerns

Never infer the generated programming model from `mode`.

They solve different problems:

```text
mode
    ↓
generated file organization

client
    ↓
generated TypeScript API programming model
```

Typical `mode` values include:

```text
single
split
tags
tags-split
```

For a small or medium project, prefer:

```ts
mode: 'single'
```

unless the existing project structure clearly benefits from another mode.

Use:

```ts
mode: 'tags-split'
```

when the API is sufficiently large and OpenAPI tags already provide meaningful
domain grouping.

Do NOT introduce `tags-split` merely because multiple endpoints exist.


# 9. Orval Axios client style

For a simple typed functional API, prefer explicitly configuring:

```ts
client: 'axios-functions'
```

Do not rely on Orval defaults when the generated API style matters.

With `axios-functions`, generated operations are intended to be consumed as
functions.

Conceptually:

```ts
import { acquireTicket } from './generated/client';

await acquireTicket(ticketId);
```

The actual function name and import path MUST be verified from generated code.


If the configuration explicitly uses:

```ts
client: 'axios'
```

Orval generates a factory-style client.

Conceptually:

```ts
import { getTicketApi } from './generated/client';

const api = getTicketApi(axiosInstance);

await api.acquireTicket(ticketId);
```

Therefore:

```text
client: 'axios-functions'
    → generated functions

client: 'axios'
    → generated factory
```

Do NOT confuse this distinction with:

```text
mode: 'single'
mode: 'tags-split'
```

`tags-split` does NOT imply a factory API.

`single` does NOT imply individually exported functions.


# 10. Generated imports

Never guess Orval exports.

After generation, inspect the actual generated files before writing application
imports.

In particular:

- Do not assume generated operations are exported from `./generated`.
- Do not assume an `index.ts` barrel exists.
- Do not assume a `tags-split` module exposes a factory.
- Do not assume a `single` module exposes individual functions.
- Do not import from a guessed path based only on the Orval configuration.

Use the API shape actually produced by the selected Orval client.

If generated imports are unexpectedly difficult or operation names are
unusable:

1. inspect `orval.config.*`;
2. inspect the OpenAPI `operationId`;
3. inspect the generated exports;
4. fix configuration or the canonical backend contract;
5. regenerate.

Do NOT manually repair generated code.


# 11. HTTP client and Axios configuration

HTTP transport configuration belongs outside the generated-code directory.

When needed, a custom Axios instance or Orval mutator can live in a file such
as:

```text
src/api/http-client.ts
```

Typical responsibilities include:

- backend base URL;
- authentication headers;
- interceptors;
- request correlation IDs;
- centralized transport-level error handling;
- response normalization when intentionally required.

Do not create a custom HTTP abstraction unless the project actually requires
one.

For a simple application using a Vite proxy and relative API paths, the
generated Axios functions may be sufficient without a custom mutator.


# 12. Base URL and Vite proxy

Never assume a hard-coded value such as:

```text
/backend/api
```

is the correct Axios `baseURL`.

Before configuring the frontend HTTP client, reason about the complete URL
composition:

```text
generated OpenAPI path
        +
Axios baseURL
        +
Vite proxy / rewrite
        ↓
actual FastAPI route
```

For example, if OpenAPI generates:

```text
/api/tickets/123
```

and Vite proxies:

```text
/api
    ↓
http://localhost:8000
```

a separate Axios prefix may not be needed.

Avoid accidental path duplication such as:

```text
/backend/api/api/tickets/123
             ^^^
```

When modifying proxy or base-URL configuration, validate at least one real
request end-to-end.


# 13. Optional custom Axios mutator

Use a custom Orval mutator only when it provides concrete value.

A possible implementation is:

```ts
import axios, { AxiosRequestConfig } from 'axios';

const axiosInstance = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL ?? '',
});

export const apiClient = <T>(
  config: AxiosRequestConfig,
  options?: AxiosRequestConfig,
): Promise<T> =>
  axiosInstance({
    ...config,
    ...options,
  }).then(({ data }) => data);
```

The corresponding Orval configuration may reference it through:

```ts
output: {
  override: {
    mutator: {
      path: './src/api/http-client.ts',
      name: 'apiClient',
    },
  },
}
```

Keep the mutator outside the generated directory.


# 14. Generated return types

Never assume an Orval-generated call returns a specific wrapper type without
checking the generated signature.

Depending on the selected client and configuration, application code may receive
a value shaped like:

```ts
AxiosResponse<T>
```

or directly:

```ts
T
```

A custom mutator can, for example, extract:

```ts
response.data
```

and return `T` directly.

Therefore, do NOT systematically write:

```ts
const response = await someGeneratedCall();
return response.data;
```

and do NOT systematically remove `.data` either.

Inspect and respect the generated return type.

TypeScript compilation should be used to enforce this contract.


# 15. Error handling

Do not wrap every generated API call in redundant `try/catch` blocks simply
because it returns a Promise.

Handle errors at the layer that owns the relevant responsibility.

Examples:

```text
Axios interceptor / mutator
    → transport concerns

frontend API/application service
    → domain-level error transformation

React component / hook
    → UI state and user feedback
```

Do not duplicate identical error transformation across every component.

Do not swallow exceptions.

Preserve enough information to diagnose HTTP failures during development.


# 16. Frontend API layer

An application-specific API layer is optional.

For example:

```text
src/api/
├── generated/
├── http-client.ts
└── services/
    └── tickets.ts
```

Use such a layer when it adds value such as:

- composing several backend operations;
- translating transport errors into domain errors;
- adapting backend data for frontend use;
- hiding transport details from application code;
- providing a stable application-facing interface.

Do NOT create one wrapper per generated operation mechanically.

For a small demonstrator, React code may call generated operations directly when
there is no useful additional abstraction.

Avoid abstraction for abstraction's sake.


# 17. Type ownership

Do not independently maintain two definitions of the same API contract.

Avoid:

```ts
// Manually recreated from a backend Pydantic model
interface Ticket {
  id: string;
  status: string;
}
```

when Orval already generated the corresponding type.

Prefer:

```ts
import type { TicketResponse } from './api/generated/models';
```

using the actual generated export path.

Frontend-only models are allowed when they represent frontend-specific state
rather than backend API contracts.

Examples include:

```text
UI state
form state
view models
component props
local filters
derived presentation models
```

Keep these concepts distinct from generated backend DTOs.


# 18. API generation workflow

When the backend contract changes, follow this flow:

```text
Pydantic / FastAPI change
        ↓
validate backend
        ↓
GET /openapi.json
        ↓
run Orval
        ↓
inspect generated output
        ↓
TypeScript compile / typecheck
        ↓
frontend tests
        ↓
end-to-end API verification
```

Do not continue implementing against stale generated artifacts after changing
the backend API.


# 19. Generation command

If the frontend does not already provide an API-generation command, adding an
explicit package script is recommended.

For example:

```json
{
  "scripts": {
    "api:generate": "orval --config orval.config.ts"
  }
}
```

Use the package manager already present in the repository.

Examples:

```bash
npm run api:generate
```

```bash
pnpm api:generate
```

```bash
yarn api:generate
```

Do not introduce a second package manager.

A shell script such as:

```text
scripts/generate_api_client.sh
```

is optional and should only be added when it simplifies the existing workflow.


# 20. Validation after generation

After generating the frontend API client, verify:

```text
/openapi.json is reachable
        ↓
Orval completes without generation errors
        ↓
generated files exist
        ↓
imports resolve
        ↓
TypeScript typecheck passes
        ↓
frontend build/tests pass
        ↓
at least one generated API call reaches FastAPI correctly
```

When practical, validate at least one representative endpoint end-to-end.

This catches configuration errors involving:

- generated paths;
- Axios base URL;
- Vite proxy;
- proxy rewrites;
- operation arguments;
- request serialization;
- response handling.


# 21. Debugging Orval integration failures

If generated API usage fails, diagnose the contract chain instead of patching
symptoms.

Inspect in this order:

```text
1. FastAPI route
2. Pydantic request / response model
3. generated /openapi.json operation
4. operationId and tags
5. Orval configuration
6. generated TypeScript exports
7. frontend import
8. Axios / mutator configuration
9. Vite proxy
10. actual browser network request
```

Typical problems include:

```text
wrong generated import path
wrong assumption about axios vs axios-functions
wrong assumption about single vs tags-split
poor or unstable operationId
duplicated base URL prefix
incorrect proxy rewrite
stale generated artifacts
manually duplicated TypeScript contract
incorrect assumption about AxiosResponse<T> vs T
```

Fix the earliest incorrect layer in the contract chain.


# 22. Scope control for time-constrained implementation

For a time-constrained implementation, prefer the simplest architecture that
satisfies the requirements.

A good baseline is:

```text
FastAPI
    ↓
OpenAPI
    ↓
Orval
    ↓
single
    +
axios-functions
    ↓
generated typed functions
    ↓
React
```

Add:

```text
custom Axios instance
service layer
tags-split
additional abstractions
```

only when requirements or project size justify them.

Do not spend implementation time introducing infrastructure without a concrete
benefit.


# 23. CI/CD and deployment

Do NOT add:

```text
Docker
Kubernetes
Helm
CI/CD pipelines
deployment manifests
additional infrastructure layers
```

unless:

- required by the requirements;
- already present and necessary;
- or directly needed to complete the requested functionality.

If CI already exists, it may validate that:

```text
OpenAPI client generation succeeds
TypeScript typechecking succeeds
generated artifacts are up to date
```

but do not introduce CI infrastructure solely because this skill discusses API
generation.


# 24. Definition of correct integration

The backend/frontend API integration is considered structurally correct when:

```text
Backend Pydantic models
        ↓
FastAPI contract
        ↓
OpenAPI
        ↓
Orval
        ↓
generated TypeScript API
        ↓
frontend consumption
```

is preserved without parallel manually maintained contracts.

The implementation should additionally satisfy these invariants:

- the backend remains the canonical API source of truth;
- repository structure is adapted rather than unnecessarily replaced;
- Orval-generated artifacts are isolated;
- generated files are never manually edited;
- Orval `mode` is not confused with Orval `client`;
- generated imports are based on actual exports;
- URL composition between browser, proxy and backend is validated;
- generated return types are respected;
- abstractions are introduced only when they add value;
- at least one representative generated API call is validated end-to-end.


# 25. Core decision rule

When uncertain, apply this rule:

```text
Do not make the repository conform to Orval.

Configure Orval to conform to the repository,
while preserving the OpenAPI → generated-client contract.
```
